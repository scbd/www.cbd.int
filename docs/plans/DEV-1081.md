## Goal

DEV-1010 records a per-language translation status map on each Intervention (`translations[lang]`) and
exposes a manual per-language request endpoint. Nothing in the staff UI reads or writes either. Add a
collapsed **Automatic translations** section at the bottom of the intervention edit dialog so a
Statement System Manager can see per-language translation status and trigger or retry translations.

Collapsed it summarises done-out-of-requested plus pending/failed counts. Expanded it shows one row per
UN language with status, message, and a request checkbox, with missing and failed languages preselected.
A Request button submits one request per selected language and names them on its label. A refresh
control re-reads server state so pending rows can be checked without reopening the dialog.

## Backend contract (given - verified against gaia@master by the ticket, not re-verified here)

- `POST api/v2021/meeting-interventions/{interventionId}/files/{fileId}/translations`,
  body `{ targetLanguage }` -> `202` + that language's status object.
- `translations[lang]` = `{ status, updatedOn, sourceFileId?, fileId?, error? }`. `error` is a raw
  `err.message` from DeepL or ConvertAPI - operator-facing text, not a curated string.
- Statuses: `pending`, `done`, `failed`. Gaia's worker never throws: on provider failure it records
  `failed` with the message and acks once, so a failed language stays failed until re-requested.
- The endpoint rejects a non-UN `targetLanguage`, and rejects `targetLanguage === sourceFile.language`.
- `UN_LANGUAGES = ar, en, es, fr, ru, zh`.
- The `PUT` that `save()` issues returns the raw intervention document, so `translations` survives a
  save and the section does not need to re-fetch afterwards.

## HARD REQUIREMENT - data safety for excluded languages

**A language holding any non-`autoTranslated` file renders as `Original` with no checkbox and can
never be selected or submitted.**

This is a data-safety rule, not presentation. Gaia's `internalAddFile` supersedes any existing file
with the same `language` **and** `contentType` into `deletedFiles` and flips its S3 ACL to private.
Translations are always `application/pdf`. Requesting a language that already holds a human-submitted
PDF would therefore **soft-delete that delegation's own submission and make it private.**

Implementation consequences, all mandatory:

1. The exclusion is computed from `hasHumanFile(lang)` - `serverFiles.some(f => f.language === lang && !f.autoTranslated)` -
   **not** from the source language alone. The source language is one instance of this rule, not the
   whole rule; a delegation can submit its own French PDF alongside an English original.
2. Excluded rows render no `<input type="checkbox">` at all, so they cannot enter `selected` even via
   a stale array. `candidateLangs` and `requestableLangs` are both derived from `rows`, so an excluded
   row is structurally absent from every selection set.
3. `request()` submits `this.rows.filter(r => selected.includes(r.lang))`, i.e. it re-derives from
   `rows` rather than trusting `selected` directly. A code that is not a selectable row cannot be posted.
4. Re-requesting a language whose only file is `autoTranslated` **is** safe by the same gaia mechanism -
   the previous AI PDF is cleanly replaced, not duplicated. That is why `done` and
   `translated (untracked)` stay manually selectable.

Gaia also rejects `targetLanguage === sourceFile.language` server-side, but that is a second line of
defence for one case only. It does **not** cover a human-submitted non-source language, so the
client-side rule above is the real guard.

`serverFiles` is the key design point. It comes from the `intervention` **prop** and is only ever
replaced by a `getInterventionById` result. It is **never** the modal's `this.files`
(`edit-intervention-modal.vue:213`), because `save()` rebuilds that as
`addedFiles.concat(updatedFiles)` (`:393`), putting newly added files first and changing which file
is "first non-`autoTranslated`".

Refresh replaces `serverFiles` as well as `translations`. This is required, not extra: rows depend on
which `autoTranslated` files exist, so refreshing statuses without refreshing files would make a
just-completed translation render as `done (file removed)`. The decision's "must not touch ... the
local `files` array" refers to the **modal's** editable array, which this component never reads or
writes - so unsaved edits are still safe. See Open question 3.

### Computeds

```
sourceFile        = serverFiles.find(f => !f.autoTranslated) || null
visible           = !!intervention._id && !!sourceFile && !!sourceFile._id
orderedLangs      = sourceFile ? [sourceLang, ...UN_LANGUAGES.filter(l => l !== sourceLang)]
                               : UN_LANGUAGES                       // always six entries
rows              = orderedLangs.map(buildRow)
candidateLangs    = rows.filter(r => r.preselect).map(r => r.lang)
requestableLangs  = rows.filter(r => r.selectable).map(r => r.lang)
summary           = { requested, done, pending, failed }  // counted over Object.values(translations)
headerText        = summary.requested
                      ? `Automatic translations ${summary.done}/${summary.requested} (${summary.pending} pending, ${summary.failed} failed)`
                      : 'Automatic translations - none requested'
anySelected       = selected.length > 0
isIndeterminate   = selected.length > 0 && selected.length < requestableLangs.length
requestLabel      = `Request (${rows.filter(r => selected.includes(r.lang)).map(r => r.lang).join(', ')})`
```

`summary` counts are map-derived, exactly as decided: `requested` is the number of entries in
`translations`; `done` / `pending` / `failed` count entries with that `status`. `done` therefore counts
a `done` entry even when its file was removed - the `(file removed)` nuance is a row-level display
concern, and the collapsed header stays a faithful summary of the map.

### `buildRow(lang)` - the single status decision, in order

Let `entry = translations[lang]`,
`hasHumanFile = serverFiles.some(f => f.language === lang && !f.autoTranslated)`,
`hasAiFile = serverFiles.some(f => f.language === lang && f.autoTranslated)`.

| # | Condition                            | `status`          | `selectable` | `preselect` |
| - | ------------------------------------ | ----------------- | ------------ | ----------- |
| 1 | `hasHumanFile`                       | `original`        | **false**    | false       |
| 2 | `!entry && hasAiFile`                | `untracked`       | true         | false       |
| 3 | `!entry`                             | `missing`         | true         | **true**    |
| 4 | `entry.status === 'done' && !hasAiFile` | `doneFileRemoved` | true       | **true**    |
| 5 | `entry.status === 'done'`            | `done`            | true         | false       |
| 6 | `entry.status === 'pending'`         | `pending`         | true         | false       |
| 7 | `entry.status === 'failed'`          | `failed`          | true         | **true**    |
| 8 | anything else (unknown status)       | raw `entry.status` | true        | false       |

Rule 1 subsumes the source language (the source file is itself a human file in the source language),
so the source row renders `Original` with no checkbox by the same rule that protects any other
human-submitted language. The source language is special **only** in row ordering (pinned first).
Rule 8 exists so a future gaia status renders as itself rather than as `missing`.

`row.message`:

```
rowErrors[lang]                                              // a rejected POST wins
|| (status === 'pending' && entry.updatedOn
      ? `requested ${asDateTime(entry.updatedOn).toRelative()}` : '')
|| (status === 'failed' ? (entry.error || '') : '')
|| ''
```

Truncation of the `failed` provider message is CSS (`white-space:nowrap; overflow:hidden;
text-overflow:ellipsis; max-width`) with `:title="row.message"` on the cell, so the full text is in
the tooltip and no JS string slicing is needed.

### Header checkbox - two click states, three glyphs

- `:checked="anySelected"`, `:indeterminate.prop="isIndeterminate"` (Vue 2.7 `.prop` modifier - no
  ref or directive needed), `@change="toggleAll"`, `type="checkbox"`.
- `toggleAll()`: `this.selected = this.selected.length ? [] : this.candidateLangs.slice()`.
  Clicking with nothing selected selects the candidates (missing, failed, `done (file removed)`);
  clicking with anything selected clears everything.
- The `[-]` glyph is display-only: it never changes what a click does.

Per-row checkboxes use `v-model="selected" :value="row.lang"` (Vue 2 array binding), rendered only
when `row.selectable`.

### Expand / collapse

`toggleExpanded()`:

```js
this.expanded  = !this.expanded;
this.selected  = this.expanded ? this.candidateLangs.slice() : [];
this.rowErrors = {};
```

Expanding always recomputes the preselect from current status; a manual selection is deliberately not
preserved across a collapse.

### `request()`

```js
const langs = this.rows.filter(r => this.selected.includes(r.lang)).map(r => r.lang);  // safety re-derive
const interventionId = this.intervention._id;
const fileId         = this.sourceFile._id;

this.busy = true;
this.rowErrors = {};

const results = await Promise.all(langs.map(lang =>
  this.api.requestInterventionFileTranslation(interventionId, fileId, lang)
    .then(status => ({ lang, status }))
    .catch(err   => ({ lang, error: (err && (err.message || err.code)) || 'Request failed' }))
));

for(const { lang, status, error } of results) {
  if(error) this.$set(this.rowErrors,    lang, error);
  else      this.$set(this.translations, lang, status);
}

this.selected = this.candidateLangs.slice();
this.busy     = false;
```

- One POST per selected language, fired together; each promise catches its own rejection, so
  `Promise.all` never rejects and a partial failure never aborts the rest.
- `$set` is required - these are new keys on a plain object in Vue 2.
- Each `202` body is merged into `translations`, so a successful row shows **real server state**, not
  an optimistic guess.
- A rejected POST leaves that row's status untouched and puts the message in its Message column.
  **No global alert** - `error` on the modal (`edit-intervention-modal.vue:144-146`) is not touched.
- Re-deriving `selected` from `candidateLangs` afterwards deselects rows that are now `pending` while
  leaving a rejected row selected and ready to retry (AC 14).
- Request acts on server state immediately and needs a persisted `fileId`. No dirty-form check;
  static helper text under the section states that it reflects saved server state.

### `refresh()`

```js
this.busy = true;
this.refreshError = null;
try {
  const fresh = await this.api.getInterventionById(this.intervention._id);   // api.js:91-94
  this.translations = { ...(fresh.translations || {}) };
  this.serverFiles  = (fresh.files || []).slice();
  this.rowErrors    = {};
  if(this.expanded) this.selected = this.candidateLangs.slice();
} catch(err) {
  this.refreshError = (err && (err.message || err.code)) || 'Refresh failed';
} finally {
  this.busy = false;
}
```

Touches only this component's own state. It never writes to the modal's data, so unsaved form edits
and the editable Files list survive a refresh. No polling, no push channel: a pending row changes only
on refresh or on reopening the dialog.

### Visibility

`v-if="visible"` on the section root: `!!intervention._id && !!sourceFile && !!sourceFile._id`.
Unsaved files have no `_id`, and `serverFiles` only ever holds saved files. Once visible the section
always renders, including when `translations` is absent - that is the only path to a first request.

## Manual verification script (from the ticket's Testing Decisions)

Manual browser verification only. `www.cbd.int` has no frontend test infrastructure - `package.json`
has no test script and no runner, and `test/` holds only 2021-vintage `data/` and `directives/`
fixtures with nothing to run them. This story adds none.

Against a staging session, as an admin-role user (`Administrator`, `EditorialService` or
`StatementAdmin` - required to reach the route at all):

1. Section **hidden** on a statement with no saved file.
2. Section **visible and collapsed**, with the "none requested" wording, once a file exists.
3. Expanding **preselects** missing and failed.
4. The source row shows `Original` with **no checkbox**.
5. A language with a human-uploaded file shows `Original` and **cannot be selected**.
6. The header checkbox selects the candidates, then clears them.
7. The Request label lists the selected codes, and the button is disabled when the selection is empty.

### Explicit safety case (must not be skipped)

With a **human-submitted French PDF** present on the statement:

- French must be **unselectable** - rendered `Original`, no checkbox, absent from `candidateLangs`
  and from `requestableLangs`, and impossible to include in a Request.
- Request other languages (for example `es`, `zh`).
- Afterwards the **French original must still be present and public**: it appears in the dialog's
  Files list, its "Visible on website" state is unchanged, and its URL still resolves publicly.
  Nothing may have moved into `deletedFiles` and no ACL may have flipped to private.

## Open questions and contradictions

Three, all recorded rather than silently resolved. None is a blocker for steps 1-8; item 1 needs a
human call before the PR is declared green.

### 1. `npx eslint` cannot pass in this repo (contradiction - needs a human call)

The ticket's Testing Decisions and the work order both require "`npm run build` and `npx eslint` must
pass". Verified in this checkout:

- `eslint` is **not** a dependency (`package.json` has no `eslint` in `dependencies` or
  `devDependencies`) and is not installed (`ls node_modules | grep -ix eslint` -> no match;
  `which -a eslint` -> `eslint not found`).
- There is **no** eslint configuration anywhere in the repo: no `.eslintrc*`, no `eslint.config.*`
  (only a legacy `.jshintrc`).
- `npx --no-install eslint --print-config app/components/meetings/api.js` resolves ESLint 10.8.0 from
  the npm cache and **fails**: `ESLint couldn't find an eslint.config.(js|mjs|cjs) file.`

So `npm run eslint` (`npx eslint . --fix`) fails on `master` today, before any change of ours. Adding
an eslint config would be a new file and a repo-wide lint decision - out of scope for this ticket and
against the maintenance-only rule. **Proposal: treat `npm run build` as the mechanical gate and drop
the eslint requirement for this ticket (or raise it as separate tooling work).** Flagged for the human.

### 2. English language names vs the existing native-name map (decision kept, cosmetic clash noted)

The ticket decided English language names. The repo's existing map, `app/data/languages.js:2-9`, holds
**native** names (`العربية`, `English`, `Español`, `Français`, `Русский`, `中文`), and that is what
`files-view.vue:86-88` renders. The Files block directly above the new section
(`edit-intervention-modal.vue:120-125`) also uses native names in its language dropdown.

Following the decision as written means the new section shows `Arabic / Spanish / French ...` a few
pixels below a dropdown showing `العربية / Español / Français ...`. Implementing as decided with a
local six-entry `LANGUAGE_NAMES` constant (not a new shared module, not a change to
`app/data/languages.js`). Noted for the human in case the visual inconsistency is unwanted.

### 3. "Refresh updates only the translations state" needs `serverFiles` too (clarification, resolved)

The decision says Refresh "updates **only** the translations state and the derived rows - it must not
touch the form fields or the local `files` array". Taken literally that breaks AC 12 combined with
AC 13: rows are derived from *both* `translations` **and** which `autoTranslated` files exist, so
refreshing statuses without refreshing files would render a just-completed translation as
`done (file removed)`.

Resolved without changing the decision's intent: the component keeps its **own private** file
snapshot (`serverFiles`), initialised from the `intervention` prop and refreshed alongside
`translations`. The prohibition targets the **modal's** editable `files`
(`edit-intervention-modal.vue:213`) and the form fields, which this component never touches - so
unsaved edits are still safe. Recorded here because it is a reading of the decision, not a
restatement of it.

### 4. Minor, decided locally (no human input needed)

- **Request label ordering.** The ticket's example `Request (es, zh, ar)` is illustrative. Codes are
  listed in **row display order** (source first, then `ar, en, es, fr, ru, zh`) so the label is
  deterministic and does not depend on click order.
- **Empty-map header wording.** The header format is `Automatic translations {done}/{requested}
  ({n} pending, {n} failed)`, but the Testing Decisions ask for "none requested wording" when nothing
  has been requested. Both are honoured: `requested === 0` renders
  `Automatic translations - none requested`, otherwise the counted form.

## Risks

- **Data safety** is the one risk that matters. It is fully mitigated by the hard requirement above
  (no checkbox rendered, selection sets derived from `rows`, `request()` re-derives from `rows`) and
  covered by an explicit manual case.
- **Reactivity**: new keys on `translations` / `rowErrors` need `this.$set` in Vue 2. Missing it shows
  as a row that does not update after a request - caught by step 6's verify.
- **Source-file ambiguity after a save** is avoided by reading the `intervention` prop, never the
  modal's `files` (`edit-intervention-modal.vue:213`, `:393`). In practice the modal also closes on a
  successful save (`:401`), so the post-save path is not even reachable.
- **Form submission**: every control the section adds carries `type="button"`. `submitForm` at
  `edit-intervention-modal.vue:18` is undefined, so a default-type button would throw on click.
- **Known, accepted**: staff can still change an AI file's language in the Files list and desync it
  from its map entry. Out of scope; that is what `translated (untracked)` and `done (file removed)`
  surface instead of hiding.
